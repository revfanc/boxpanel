# T6.10 调研与修复记录 / PR 描述

## 根因结论与证据

1. **确认：生效阻塞订阅和面板读请求。** 原 `db.Open` 的 MaxOpenConns=1，
   `Manager.Apply` 从 BEGIN IMMEDIATE 到恢复完成一直占用该连接；订阅路由、Store.Load、
   Authenticate 及资源读取都复用它。修复前先运行 `TestApplyReadAvailability`：分别暂停
   restart / is-active，订阅、auth/me、users、settings、setup/status、rules 全部在
   500ms 请求截止后返回 500。暂停解除后，traffic_limit=1610612736 的用户创建返回 201。
   这是可确定的读取中断机制，与是否填写限额无关。
2. **确认：HTTP 写超时可能隐藏真实写入结果；无法断言真机当次错误就是此原因。**
   原 Apply 无总时限，进程互斥锁等待不可取消，正常命令与失败恢复累加；HTTP WriteTimeout=30s。
   `TestHTTPWriteTimeoutCanHideCommittedUser` 将同一机制缩放为 HTTP 20ms / 重启 80ms，
   复现客户端网络错误但限额用户已提交。`TestLimitedUserApplyTimeoutHTTP` 使用真实 HTTP server，
   验证修复后的预算先于写超时：恢复旧配置后返回明确 JSON 503，用户不提交。
   缺少真机报错正文及 journal，不能把某个 500、30s 超时或回滚失败当作已证实的历史事件。
3. **确认：所有用户变更都会整体重启内核。** users → applyResource → Manager.Apply →
   restartHealthy，无限额专用重启分支。1.14.4 的 SIGHUP 不等于保持连接的热更新：
   [官方服务管理](https://sing-box.sagernet.org/installation/package-manager/#service-management)
   仅列出 restart；[锁定版本源码](https://github.com/SagerNet/sing-box/blob/v1.14.4/cmd/sing-box/cmd_run.go#L178-L213)
   在 SIGHUP check 成功后 cancel/Close 旧实例，再重新 create。
   因此按任务明确允许的例外保留 restart，不新增不受支持的用户热更新接口，不宣称连接无损。
4. **未发现正流量上限特有的生成/校验错误。** userInput 接受非负 int64；eligibleUsers
   对零用量、正上限保留用户。并发测试实际创建 1.5 GiB 限额用户并验证 active，最终服务端
   JSON 同时包含 existing 与 limited。原有 filtered_users golden 与边界测试继续通过，
   不改 GiB 换算或过滤语义，不提前实现 T7.1。

## 修复

- 同文件独立只读 WAL 池（mode=ro、query_only、deferred BEGIN，最多 8 连接），用于订阅、
  会话检查和面板读取。写池仍单连接、BEGIN IMMEDIATE；mutation/check/替换/重启/健康检查/
  防火墙/commit/回滚保持同一事务及原 pending/generation 恢复机制。
- 生效中读上一份已提交快照，不显示候选用户。慢 restart / is-active 的最终测试中，
  九个数据读取接口最长约 0.4ms（本机注入测试结果，不代表公网延迟），均小于 1 秒。
  logs/config 保留稳定文件与脱敏凭证锁，忙时立即 503，跨进程锁等待最多 100ms。
- Apply 正常工作含排队最多 12s，独立恢复最多 12s，入口起绝对总预算 24s < HTTP 30s。
  总超时返回 503 + Retry-After + 下一步提示，前端统一显示「正在生效，请稍后刷新」，保留输入。
  恢复失败/提交结果不确定优先保持 500、保留 pending/bak，下次先恢复；不后台继续提交写操作。
- apt update/install、dnf 锁错误有界重试最多 300s，每次等待最多 5s，提示系统正在自动更新。
  apt 显式关闭内部锁等待、dnf exit_on_lock=True，避免叠加/无限等待；非锁错误及权限错误立即失败。
  不删除锁文件、不 kill 进程。DNF ProcessLockError 的实际提示与退出码依据
  [官方 lock.py](https://github.com/rpm-software-management/dnf/blob/master/dnf/lock.py) 和
  [CLI 处理](https://github.com/rpm-software-management/dnf/blob/master/dnf/cli/main.py)。
- SPEC §7、API、FRONTEND、INSTALL 与 TASKS 同步。没有新增依赖、内核字段、golden 内容或供应链策略变动。
