## 问题与最终行为

原测试把所有资源写入等同于 check/替换/重启，与审查者新增的配置不变短路冲突。
现在所有资源写入仍调用同一个 Manager.Apply，在同一锁和事务中生成配置，再分两条路径：

- 非 nil mutation、已有配置且逐字节相同、防火墙计划相同、is-active 成功：只提交资源变更
  以及 applied_firewall/applied_users/apply_generation，不写临时文件/配置/备份/新 pending，
  不 check、不重启、不同步防火墙。运行状态探测仍执行。
- 显式 Restart/Startup/CLI apply（nil mutation）、未运行/状态探测失败、缺少配置、字节不同
  或计划不同：保持 check → 原子替换 → 重启 → 健康检查 → 防火墙 → 提交及失败回滚。
  Hysteria2 仅跳跃范围变化也属于此路径。

补齐短路的 COMMIT 错误处理：丢弃可能仍保留 SQLite 事务的底层连接，再用有界独立 context
核对 generation；确认未提交才报告失败，确认已提交返回成功，无法确认则返回 500 及核对建议。
没有外部状态变化，因此 DB 失败不触发服务重启补偿，也不创建新 pending。
已有 pending 必须先恢复/核对并清理，再尝试短路；未提交的 pending 恢复本身可能重启。
两条路径共用生效记账函数，防止 applied_users 等记录偏离。

## 哪些用户操作影响其他连接

下表以**无待恢复 pending、内核运行、当前配置/防火墙计划匹配**为前提；最终由生成结果决定，
没有接口白名单或测试专用开关。

| 用户操作 | 是否重启并中断其他在线连接 |
|---|---|
| 修改上限/到期时间，用户仍保持有效（或仍保持无效） | 否 |
| 修改备注、每月重置日 | 否 |
| 重置订阅 token | 否；旧订阅链接失效，连接凭证不变 |
| 手动/月度重置流量，有效用户集合不变 | 否；epoch 仍推进，跨重置连接重建采集基线 |
| 相同 enabled 的重复启停请求 | 否 |
| 有效用户新增/删除/启停/改名 | 是；认证用户或 auth_user 路由发生变化 |
| 重置有效用户的连接凭证，存在使用该凭证的启用入站 | 是 |
| 修改限额/有效期或清零，导致用户从有效变无效或恢复 | 是 |
| 删除/改名/重置凭证等操作作用于已被排除的用户，生成结果不变 | 否 |
| 显式重启、生产启动重新生效 | 是，即使字节相同 |

节点备注和 Reality 客户端 fingerprint 的编辑也不再重启；节点服务参数、端口、启停、
跳跃计划或服务端 BT 设置变化仍走完整生效。

前端将一律保存中断的文案改为条件提醒：新增、有效用户改名/有效性改变、删除/停用/连接凭证重置、
启用可恢复用户及节点配置变更时显示。普通上限/到期/备注/月度计划编辑、token 和流量重置不显示
一律中断提醒。按任务要求清零确认仅说明清零与恢复后果；清零恢复超额用户时后端仍可能重启。
提示基于页面快照估计，后台并发变化、内核停止或 pending 恢复仍由后端实际判定。
